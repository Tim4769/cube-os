Continued testing the Rev A PCB while waiting for the correct battery cable. Yesterday's oscilloscope measurements showed that Wi-Fi startup pulled TP6 from around 3.3V down to around 2V, so today I wanted to find out whether the rest of the ESP32 and PCB worked normally when Wi-Fi was disabled.

I then measured pad 1 of both servo connectors with the FNIRSI DSO-510. On both M1 and M2, pad 1 is the PWM signal, pad 2 is `+BAT`, and pad 3 is GND. I used the connector GND as the oscilloscope reference and measured pad 1 with the servos disconnected.

The results were:

- M2 pad 1: 50Hz, 7.45% duty cycle, around 3.22V peak-to-peak
- M1 pad 1: 50Hz, 7.50% duty cycle, around 3.22V peak-to-peak
- Both duty cycles correspond to a pulse width of approximately 1.5ms, which is the expected servo center signal

This confirmed that the 14-bit ESP32-S3 LEDC configuration works and that both PWM signals reach their correct connector pads. I did not connect physical servos because their middle connector pins use `+BAT`, and I am still waiting for the battery adapter.

After the power and PWM tests passed, I started adding a separate sensor module. I created `Sensors.h` and `Sensors.cpp` so sensor code would stay separate from movement, networking, and the main firmware control flow.

The first test was an I2C scanner. The Rev A I2C bus uses:

```cpp
constexpr int I2C_SDA_PIN = 8;
constexpr int I2C_SCL_PIN = 9;
```

I started the bus at the standard 100kHz speed:

```cpp
bool started = Wire.begin(I2C_SDA_PIN, I2C_SCL_PIN, 100000);
```

The scanner checks normal I2C addresses from 1 through 126. For every address, it begins an empty transmission and checks the result returned by `Wire.endTransmission()`. A result of zero means a device acknowledged the address.

The expected Rev A devices are:

- `0x10`: VEML7700 ambient-light sensor
- `0x20`: TCA6408 GPIO expander
- `0x44`: SHT45 temperature and humidity sensor
- `0x6A`: ISM330DHCX accelerometer and gyroscope

I added a small `switch` function that converts each known numeric address into a readable device name. I kept the scanner output simple and removed the extra leading-zero formatting because it did not change the scan itself.

While writing the scanner, I learned several C++ concepts:

- Headers from Arduino and installed libraries normally use angle brackets, such as `#include <Wire.h>`
- Project headers normally use quotation marks, such as `#include "Sensors.h"`
- `const char*` represents a pointer to read-only character data, which is how the device-name function returns fixed text
- A `switch` compares one value with several exact `case` values
- `0x` marks a hexadecimal number in source code, while `HEX` tells `Serial.print()` how to display an existing number
- `uint8_t` is an unsigned 8-bit integer from 0 to 255, which is large enough for an I2C address
- `unsigned long` is used for larger positive values such as the result of `millis()`
- `Serial.print()` stays on the current output line, while `Serial.println()` finishes the line

I then added the ISM330DHCX driver using the chip-specific class supplied inside Adafruit's larger LSM6DS-family library:

```cpp
#include <Adafruit_ISM330DHCX.h>

Adafruit_ISM330DHCX imu;
```

The physical sensor is an ISM330DHCX. The installed package is named `Adafruit LSM6DS` because Adafruit groups several related ST sensors into one library and shares their common accelerometer and gyroscope code.

I added two state variables:

```cpp
bool imuReady = false;
unsigned long lastImuPrintTime = 0;
```

`imuReady` prevents the firmware from reading the IMU unless initialization succeeds. `lastImuPrintTime` remembers the previous print time so measurements can be printed every 250ms without using a blocking `delay()`.

The initialization code connects to address `0x6A` using the existing I2C bus:

```cpp
if (!imu.begin_I2C(IMU_ADDRESS, &Wire)) {
  Serial.println("Failed to initialize ISM330DHCX");
  return;
}

imuReady = true;
```

The `!` reverses the Boolean result, so the error block runs only when `begin_I2C()` returns false. The `return` exits sensor setup after a failure, so `imuReady = true` is reached only after successful initialization.

I configured the IMU for basic hand movement and tilt testing:

```cpp
imu.setAccelRange(LSM6DS_ACCEL_RANGE_4_G);
imu.setGyroRange(LSM6DS_GYRO_RANGE_500_DPS);
imu.setAccelDataRate(LSM6DS_RATE_104_HZ);
imu.setGyroDataRate(LSM6DS_RATE_104_HZ);
```

The repeating update function uses this non-blocking timing check:

```cpp
unsigned long now = millis();

if (now - lastImuPrintTime < IMU_PRINT_INTERVAL_MS) {
  return;
}

lastImuPrintTime = now;
```

If less than 250ms has passed, the function returns immediately. Once 250ms has passed, it saves the new time and reads another sample.

The Adafruit driver fills three `sensors_event_t` containers:

```cpp
sensors_event_t acceleration;
sensors_event_t gyro;
sensors_event_t temperature;

imu.getEvent(&acceleration, &gyro, &temperature);
```

The `&` passes the memory address of each container so `getEvent()` can place new measurements inside it. Values are then accessed through fields such as:

```cpp
acceleration.acceleration.x
gyro.gyro.x
temperature.temperature
```

The repeated `gyro.gyro.x` naming is because the first `gyro` is my event variable, the second is the gyro section inside the generic Adafruit event structure, and `x` is the axis value. The IMU temperature is the chip's internal temperature and is not as suitable for room-temperature measurement as the separate SHT45.

I found and fixed several code problems while integrating the module:

- `scanI2CBus()` was missing its closing brace, which accidentally placed later function definitions inside it
- An IMU error `Serial.println()` was missing its final semicolon
- `Wire.begin()` was being called in both `setupSensors()` and `scanI2CBus()`, so I removed the duplicate call from the scanner
- `updateSensors()` needed to be called from `firmwareLoop()` for repeated measurements
- `setupSensors()` was temporarily missing from `firmwareSetup()`, so `imuReady` stayed false and `updateSensors()` immediately returned

The missing `setupSensors()` call caused a confusing test. PlatformIO uploaded successfully, and Device Monitor showed all the PWM messages, but no sensor messages appeared. The correct startup sequence is:

```cpp
setupSensors();
```

inside `firmwareSetup()`, followed by:

```cpp
updateSensors();
```

inside `firmwareLoop()`.

The USB port also appeared as `/dev/cu.usbmodem1101` instead of the earlier `/dev/cu.usbmodem101`. This is normal for native USB because macOS can assign a different device name when the ESP32 resets, switches between bootloader and firmware modes, or reconnects. `pio device list` shows the current port.

After restoring `setupSensors()`, uploading again, and opening Device Monitor at 115200 baud, the sensor code worked. The I2C scan and ISM330DHCX initialization messages appeared, followed by live acceleration, gyroscope, and internal-temperature readings. Tilting and rotating the PCB changed the appropriate values, confirming that the ESP32 can communicate with the onboard IMU and read real measurements.
