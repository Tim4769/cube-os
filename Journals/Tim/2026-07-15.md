# Journal — 2026-07-15

- Author: Tim (`timwang007`)
- Created at: 2026-07-15

Started testing the Rev A PCB because my Mac could not detect the ESP32-S3 when I connected the USB-C cable. At first I thought the ESP32 or the cable might have a problem, so I started measuring the test points to find where the power stopped.

The first measurements were:

- TP2 was around 5V, so USB power was reaching the PCB
- TP5 was around 4.47V
- TP6 and TP4 were 0V
- TP6, TP10, and TP11 stayed at 0V in both switch positions
- TP5 did not change when I moved the switch

This meant the BQ24074 power path was working up to TP5, but the TPS63802 was not producing the 3.3V rail for the ESP32.

I measured the switch pins and found that the outside pin was always around 4.47V while the inside pin was always 0V. Using continuity mode, I realized that the installed switch did not connect the middle pads in the way the schematic expected. In one position, pads 1, 4, and 5 were connected together.

In the schematic, pad 5 is connected to the TPS63802 input and pad 2 is connected to its EN pin. Because the real switch contacts did not connect pads 5 and 2, moving the switch never enabled the regulator. I soldered a jumper between pads 1 and 2, so when the switch connects pad 5 to pad 1, the voltage also reaches pad 2 and enables the TPS63802.

After adding the jumper, macOS finally showed this message:

```text
Allow accessory to connect?
Espressif USB JTAG/serial debug unit
```

The ESP32 also appeared as a port similar to:

```text
/dev/cu.usbmodem101
VID:PID = 303A:1001
Description = USB JTAG/serial debug unit
```

This confirmed that the ESP32 had power and that the UGREEN USB-C cable could carry both power and data.

I also changed the PlatformIO configuration from the generic ESP32 target to the ESP32-S3 target:

```ini
[env:cubeos-reva]
platform = espressif32
board = rymcu-esp32-s3-devkitc-1
framework = arduino

build_flags =
  -DARDUINO_USB_CDC_ON_BOOT=1

lib_deps =
  adafruit/Adafruit LSM6DS
  adafruit/Adafruit BusIO
  adafruit/Adafruit Unified Sensor

monitor_speed = 115200
monitor_rts = 0
monitor_dtr = 0
upload_speed = 115200
```

`ARDUINO_USB_CDC_ON_BOOT` enables serial over the ESP32-S3 native USB connection. I also learned that RTS and DTR are old serial control signals that ESP boards can reuse to control reset and boot mode. Setting both monitor values to 0 prevents the monitor from intentionally holding those signals active.

The first recovery upload used:

```bash
cd "/Users/a1/Desktop/Cube OS/Firmware"
pio run -e cubeos-reva --target clean
pio run -e cubeos-reva --target upload --upload-port /dev/cu.usbmodem101
```

I also used the BOOT and RESET buttons for the first recovery upload. Before this, the ESP32 printed `invalid header: 0xffffffff`, which meant it was reading erased flash instead of a valid firmware image. Cleaning removed the previously compiled files after changing the board target, but the main fix was getting the power working, entering download mode, and writing a complete valid image. Later uploads started working automatically without pressing the buttons.

After uploading, I found another issue in the device monitor:

```text
ledcSetup(): No more LEDC channels available! (maximum 8) or bit width too big (maximum 14)
LEDC is not initialized
```

The servo PWM code used 16-bit resolution, but this ESP32-S3 Arduino setup only supports up to 14 bits. I changed:

```cpp
constexpr int SERVO_PWM_RESOLUTION_BITS = 16;
```

to:

```cpp
constexpr int SERVO_PWM_RESOLUTION_BITS = 14;
```

The monitor also printed `nvs_open failed: NOT_FOUND`. This was not the reset problem. It only meant that the fresh ESP32 did not have saved Wi-Fi credentials yet, so the firmware correctly started setup mode.

The firmware reached:

```text
Setup access point started
Network name: CubeOS-Setup
Setup URL: http://192.168.4.1
Web server started
```

Then the USB device disappeared and the ESP32 rebooted. I also tried uploading without opening Device Monitor, but the `CubeOS-Setup` network still did not stay visible. This made it less likely that the monitor itself was causing the reset.

At first I thought the Wi-Fi current spike might be causing a power problem, so I used a FNIRSI DSO-510 oscilloscope. I used X10 on both the probe and scope, DC coupling, 1V/div, 10ms/div, Single trigger mode, and a falling-edge trigger. The scope only has one channel, so I repeated the startup separately for each test point.

The scope results were:

- TP6 dropped from around 3.3V to around 2V
- TP5 dropped from around 4.47V to around 3.32V
- TP2 did not cross the 4.72V falling trigger threshold

![TP6 3.3V rail Wi-Fi startup dip](../../PCB/Rev%20A/testing/TP6_3V3_Rail_WiFi_Startup_Dip_3V3_to_2V.bmp)

![TP5 BQ24074 output Wi-Fi startup dip](../../PCB/Rev%20A/testing/TP5_BQ24074_OUT_WiFi_Startup_Dip_4V47_to_3V32.bmp)

The TP6 measurement finally confirmed that this is a real power reset. Around 2V is far below what the ESP32-S3 needs, which explains why USB disconnects and the setup network disappears.

Since TP5 also drops but TP2 stays above 4.72V, the collapse starts inside the BQ24074 power-path section instead of at the Mac or USB cable. The switch jumper only carries the TPS63802 enable signal, not the regulator load current, so the jumper is probably not causing the TP5 voltage drop.

I measured R5 with the board disconnected and got 3.3kΩ, which matches the BOM. R5 connects to ILIM and controls the BQ24074 USB input-current limit. For this resistor range, the typical limit is around:

```text
1525 / 3300 = 0.462A
```

R6 is separate and controls battery-charging current. The ILIM setting applies to the total input current used by the system and battery charging. During all these measurements, I had no battery, servos, screens, camera, or other external parts connected. A possible explanation is that the ESP32 Wi-Fi startup reaches the input limit, and there is no battery attached to supplement the short current spike.

I checked whether the Mac could show the board's real current draw, but macOS only reports USB device or requested-power information, not a useful live measurement of a short transient. I would need an inline USB-C power meter or a bench supply with current measurement to see the actual peak.

The next test is to connect a correct 1S 3.7V LiPo battery and see whether it keeps TP6 at 3.3V when Wi-Fi starts. The battery connector on the PCB is JST-PH with two pins and 2mm pitch:

- J1 pin 1 is GND and connects to TP1
- J1 pin 2 is battery positive and connects to TP3
- The mating housing is PHR-2

My battery has a different connector, so I am going to make an adapter instead of soldering directly to the battery or PCB. I will use around 0.1m of 26AWG wire, which is inside the JST-PH contact's supported wire range. Before connecting it, I need to verify the polarity with a multimeter because battery connectors can use the same housing with the red and black wires reversed.

If TP6 stays near 3.3V and `CubeOS-Setup` remains visible with the battery connected, it will confirm that the no-battery/current-limit condition caused the reset. If TP6 still collapses, I will need to investigate the BQ24074 soldering and control pins, the TPS63802, or an unexpectedly large load somewhere on the PCB.
